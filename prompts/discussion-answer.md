## Your task: the first answer to discussion #{issue}

Someone started discussion #{issue} in the GitHub Discussions of the repository, in a category whose questions the maintainers want answered. Your answer is posted there as a comment; the maintainers and the community read it, and the person who asked may mark it as the answer. The context files:

- `{context}/discussion.md`: the discussion with its comments and their replies. Read it completely first.
- `{context}/issues.jsonl`: the issues of the repository, one JSON object per line with number, title, state, state_reason, labels, dates, the number of comments, `closed_by` (the pull request that fixed it, if one did) and an excerpt: every open issue, the {max_issues} closed ones that changed last, and older ones that a search for the words of this discussion found. Search it with Grep. `{context}/issues/<number>.md` holds the whole text of each of them.
- `{context}/discussions.jsonl`: the {max_discussions} other discussions that changed last, each with its category, whether it has an answer, an excerpt and the excerpt of its answer.

The latest release is {release}.

1. **Understand the question:** what the person wants to do or know, what they tried, and the versions and the setup that matter for this project (the project description names them).
2. **Investigate in the repository.** Read the documentation of the topic (for someone who writes in another language also the documentation in their language, if the project has some), especially a guide, a FAQ or a troubleshooting page, and the changelog: did a newer version than theirs change it? Then look at the code and the configuration involved. Check every option, setting and command that you name in the code or the documentation.
3. **Look for the same question.** Grep `issues.jsonl` and `discussions.jsonl` with several sets of keywords, in English and in the language of the question: an answered discussion, a closed issue with a fix, an open issue that tracks the same. Read the promising lines completely, and the whole text in `issues/` of an issue whose excerpt isn't enough.
4. **Decide what it is.** `kind` is `"question"` for a question about using, setting up or understanding the project; `"bug"` when it reports that something doesn't work as documented; `"feature"` when it asks for something that the project doesn't do; `"spam"` for advertising, nonsense and posts that have nothing to do with this project, which get no answer; then keep all texts short.
5. **Write the answer.**
   - `answer`: the answer for the person who asked, who uses the project: what to do, step by step where it helps, with the settings, commands and versions involved, and why. At most about 300 words. Name the discussions and issues that help as #123. Say "probably" or "possibly" where you infer, and when the repository doesn't settle the question, say so and what would. For a bug or a feature, say what you found, such as a workaround or what exists today; the script adds a sentence that asks for an issue.
   - `maintainer_summary`: for the maintainers, as the rules say: the question and the gist of your `answer` and `missing_information` in their language, or empty when `language` is theirs.
   - `missing_information`: only what you need to answer, or to answer better, and what the discussion doesn't say yet, each as a concrete request that says where to find it; empty when the answer is complete.
   - `references`: the files that the answer rests on, at most six. `path` is relative to the repository root. Give `line` for code (the line that matters) or `anchor` for a heading of a Markdown file (GitHub's anchor, such as `no-realtime-updates`), and a short `reason`. Prefer documentation in the language of the question.
   - `sensitive_data`: `"secret"` when the discussion or a comment shows a token, a key, a password or another credential; `"personal"` when it shows other personal data, such as an e-mail address, a public IP address or the address of a private server; otherwise `"none"`. Placeholders, example values, variable names and the names of settings are not sensitive data.
   - `security_report`: true when the discussion reports a security vulnerability. Then keep `answer` to one neutral sentence without any detail of the vulnerability, because the log of the run can be public, and leave `maintainer_summary`, `missing_information` and `references` empty.
