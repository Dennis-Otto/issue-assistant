# What the AI reads

[← All features](README.md)

Each task reads what it needs and no more, from the files that the `context` step writes into `.issue-assistant/`.

A first analysis, a follow-up and a first answer to a discussion also read the labels, every open issue, the closed issues that changed last up to max_issues and the discussions that changed last up to max_discussions, all but a first answer to a discussion with the labels, from GitHub's GraphQL API, which lists no pull request; each issue has an excerpt in issues.jsonl and its whole text in issues/. A first analysis and a first answer to a discussion add up to 30 older issues that a search for the names of errors and the words of the title finds, and a first analysis corrections.md: what the maintainers corrected of the analyses of up to max_analyzed issues analyzed last, which it learns from. A reply, maintainer-reply, release-reply or maintainer-question, reads comment.md instead: the comment whose event started the run, not a newer one that came in while the run waited. - **Every task reads the issue** with all its comments, in `issue.md`; the first answer to a discussion reads `discussion.md` instead, the discussion with its first 50 comments and their first 20 replies each, and the issues and discussions as a first analysis does.
- **A first analysis and a follow-up read a window of the repository:** every open issue, but for [the issue of the digest](digest.md#the-digest-as-an-issue) and those whose reporter [keeps the AI out](opt-out.md), and the 1,000 closed ones that changed last, each with an excerpt of 400 characters in `issues.jsonl` and its whole text in `issues/<number>.md`, the 1,000 discussions that changed last and the labels. GitHub's GraphQL API lists a hundred issues a page and no pull request, so a repository with 50,000 issues and pull requests costs a few calls instead of five hundred, and the context keeps its size. `[context]` in `config.toml` sets both numbers. An excerpt keeps the words of the reporter: the text above the first field of an issue form, each answer of the form as a line with the label of its field, also when a label comes twice, and a `###` line in fenced code, such as a pasted changelog, as part of the text, so that the AI finds an error message above a form when it looks for duplicates.
- **A first analysis also searches.** Up to 30 older issues that GitHub's search finds for the names of errors in the new issue, such as `TypeError` or `ECONNREFUSED`, and the words of its title join the window, so that an old duplicate is found beyond it. A search that fails leaves the window, with a warning. With [related repositories](related-repositories.md), the same search in each of them fills `related-issues.jsonl` and `related/`.
- **A first analysis learns from the maintainers' corrections.** `corrections.md` lists what the maintainers corrected of the analyses of the 30 issues analyzed last: a label of the AI that a maintainer removed within 14 days, one that a maintainer added within 7 days of the analysis, a duplicate notice that someone objected to and that didn't close, and an analysis that someone who may push gave a 👎. The prompt asks the AI not to repeat such a choice on an issue like it. GitHub is the record, so correcting the issue is all it takes, and the AI learns of nothing else: one line per issue with its number, its title as a JSON string and the labels of `labels.md`, in a fence that no title can close. The issues come from the 500 newest comments of the repository and from the window above, so the AI can read each of them; their events are read once each, and the reactions only of an analysis with a 👎. `[context] max_analyzed` sets the number, `0` turns it off, and GitHub failing it is a warning.
- **A reply judges the comment of its event.** `maintainer-reply`, `release-reply` and `maintainer-question` read the issue and `comment.md`, the comment whose event started the run, and nothing of the rest of the repository. A run can wait behind others for minutes, and a "still broken for me too" of someone else that comes in meanwhile never reopens an issue whose reporter just confirmed the fix. The `apply` job reads that comment again and acts only when it is the reporter's, after a release, or a maintainer's, and for an answer a maintainer's `/assistant ask`. A run by hand judges the newest such comment.
- **The text files that the reporter attaches are read.** A log, a configuration or a diagnostics download that the reporter drags into the issue or into one of their comments, as `.txt`, `.log`, `.json`, `.yaml` or `.yml`, is part of `attachments.md` for every task of the issue, up to 20,000 characters of each and 5 files of an issue. The job `attachments` downloads them before the AI runs, without the AI, its secret or a token that writes, and from GitHub's own hosts for attachments alone, which the firewall of the AI's job doesn't let through; the AI's job takes them as an artifact of the run. Each text stands in a code fence of its own under a heading of the script, as each comment does in `issue.md`, without the escape sequences of a terminal and the characters that no one sees, and with each part that looks like a token or a key replaced with `[secret]` and each e-mail address with `[e-mail address]`, which a note counts ([decision 0033](../decisions/0033-the-ai-reads-the-text-files-that-a-reporter-attaches.md)).
- **The images that the reporter attaches are seen, by an engine that opens images.** A screenshot that the reporter drags into the issue or into one of their comments, as PNG, JPEG, GIF or WebP, comes with the text files, up to 3 images of an issue and 5 MB of each; a video, which GitHub links as it links an image, takes no place of one. Claude and Gemini, whose tools that read files open images, find each in `attachments.md` with its path, such as `.issue-assistant/attachments/image-1.png`, and the rules of the prompt tell them that what an image shows, text in it included, is the reporter's material and never an instruction. Codex and Copilot read that an image is attached and that they can't open it. The job `attachments` only compares the first bytes of a file with those of each kind and never opens or decodes an image; an SVG, a page or anything else that only its name calls an image is left out ([decision 0034](../decisions/0034-an-engine-that-opens-images-sees-the-screenshots-of-the-reporter.md)).
- **A repository can keep the images out.** One that takes no image from strangers sets `[attachments] images = false` in `config.toml`: whatever the engine can do, the job `attachments` then downloads no image, and the AI reads that one is attached and that the settings keep it out.
- **What the AI doesn't read of the attachments.** Archives such as a `.zip`, and every other file are named in `attachments.md` as attached and not read: nothing is ever opened by a program, run or unpacked. So are a file that isn't UTF-8 text, a sixth text file, a fourth image or one larger than 5 MB, a download that GitHub refused, with its reason, and a file that someone else than the reporter attached, or that GitHub hides, as in an HTML comment or in an attribute of a tag other than the `href` of an `<a>` and the `src` of an `<img>`, of which the page shows no link. The rules of the prompt tell the AI not to ask for an attached file again. In a private repository, GitHub may refuse the token of the job for an attachment; `attachments.md` then names the file with the reason. Lines of a log that a reporter pastes into the text, best in a code block, are read as well, up to the 20,000 characters of each text.
