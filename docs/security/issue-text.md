# How the text of an issue reaches the AI

[← Security design](../security.md)

The AI learns who wrote what from `issue.md`: a heading for the issue and for each comment names the author, the role, such as reporter or maintainer, and the date, and the AI's own earlier comments are marked as its own. The text under a heading is written by anyone, so it must not be able to write such a heading itself, nor hide what the maintainer can't see:

It goes into a code fence with one backtick more than its longest run of backticks, so that no line of the text can end it. The heading above the fence, which only the script writes, names the author, the role and the date. The other issues and discussions become excerpts without HTML and definitions, lose their invisible characters too and go into JSON. - **Nothing in a text can end its fence.** A fence ends only at a line of at least as many backticks as the line that opened it, and the assistant opens it with one backtick more than the longest run in the text, at least three. So `## Comment 4 by @owner (maintainer)` in a text stays a line of that text, and so does a fence of the text's own, whatever its length. The prompt tells the AI that a fence holds only that person's text, whatever it looks like.
- **What GitHub doesn't show, the AI doesn't read.** The tag characters of Unicode, U+E0001 to U+E007F, spell a whole sentence in ASCII that no browser shows, and zero-width spaces, joiners and the controls of the direction of writing hide or reorder text. The assistant removes every format character of Unicode and every code point that Unicode calls default ignorable, such as variation selectors, which can carry a byte each, from the issue and its comments, from the excerpts of the other issues and discussions, and from the AI's answer before its checks, so that none can hide a token from them either. They go after the HTML, which goes as GitHub hides it: a zero-width space in the `-->` of an HTML comment keeps the comment from ending on GitHub, so that it hides the rest of the text, and taken out first, it would end the comment and show the AI what GitHub hides. A `<!--` without its `-->` hides the rest of the text wherever GitHub hands it on as HTML: at the start of a row, also of a quote, a list item or a footnote, after a tab and at any depth of them, and anywhere in a row of an HTML block, such as one that starts with `<div>`, `<p>` or `<?php`, also after the end of the quote or the list item that holds the block, and after a `--!>`, which ends a comment for GitHub's HTML parser but not the block. So does a quoted value of a tag in such a block that the block doesn't end, since GitHub looks for its end in the rest of the text. In a paragraph, GitHub shows such a `<!--` as text, and the AI reads it with what follows. Where it is hard to tell whether a row belongs to a block, such as in fenced code or after the end of a quote, the assistant takes the rest out rather than leave it. The excerpts of the other issues and discussions lose their HTML the same way, every tag with its attributes, before the answers of a form become lines. And the invisible characters go before the fence is chosen, so that none can split a run of backticks that would end it.
- **Nor does it read a tag that runs over several rows.** GitHub reads each row of an HTML block up to the `>` of a tag as part of the tag, past a `>` in a quoted value, also in a quote or a list item, whose marks are no end of it, and up to the end of the block when no `>` comes, or on into an HTML block that follows it; and in a paragraph, a tag that CommonMark reads as one over its rows, such as `<span` above `title="a">`. The assistant takes out such a tag with every row of it. What GitHub shows as text stays: `<a` above a row that starts a quote, a tag of a paragraph that CommonMark doesn't read as one, the tags that GitHub's filter shows as text, such as `<script`, and a tag in fenced code, also in a quote or a list item, which GitHub shows as it is. A tag on one row goes as it always did. Where it is hard to tell whether a block or fenced code holds a row, the assistant takes the tag out with it, and where it is hard to tell whether a tag goes on in the next block of a quote or a list item, the rest of the text: a block of a quote takes no row without the `>` of the quote, nor a block of a list item a row with less indentation, but a row can't always tell which quote or list item it belongs to.
- **Nor does it read a definition that GitHub hides.** GitHub shows nothing of a link reference definition, such as `[//]: # (a comment)` or `[x]: <> "a comment"`, the usual ways to write a comment in Markdown, and nothing of a footnote that no reference shows. The assistant takes both out of the issue, its comments and the excerpts of the other issues and discussions, after the HTML and outside code, and leaves `(link definition removed)` or `(footnote removed)` in the place of each, so that the AI doesn't wonder about the missing target of a `[text][label]` link. It reads them as GitHub does: a definition starts a block, also in a quote or a list item, after indented code and after HTML in a quote or a list item, and its label or title can run over several rows, while a row that looks like one in the middle of a paragraph or in fenced code stays, as GitHub shows it. A row of `=` or `-` ends a definition only where it can underline a heading: `[x]:` above `=` stays a heading, but a definition runs on over such a row without the `>` of its quote or the indentation of its list item, as GitHub reads it. Where Markdown is hard to follow exactly, such as an indented row, which may be code or belong to a list item, or a text whose HTML could start a block, the assistant takes out a definition rather than leave it. A footnote stays only for a reference that GitHub surely shows: not one in code, also in a quote or a list item, in an indented row, after a backslash, in the target of a link, in a definition or a footnote, or in a text whose HTML could hold it, since one of those could be hidden itself. A CommonMark parser checks that no definition is left, and that each footnote left has a reference. A notice in the log counts them.

Every analysis reads the excerpts of every open issue and of the closed ones that changed last, so a text planted in one issue reaches the AI again with each new issue. Its worst use would be to call new issues its duplicates, which close on their own. So only an original that a maintainer vouches for can close another issue:
