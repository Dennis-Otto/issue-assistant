# How the text of an issue reaches the AI

[← Security design](../security.md)

The AI learns who wrote what from `issue.md`: a heading for the issue and for each comment names the author, the role, such as reporter or maintainer, and the date, and the AI's own earlier comments are marked as its own. The text under a heading is written by anyone, so it must not be able to write such a heading itself, nor hide what the maintainer can't see:

- **Nothing in a text can end its fence.** A fence ends only at a line of at least as many backticks as the line that opened it, and the assistant opens it with one backtick more than the longest run in the text, at least three. So `## Comment 4 by @owner (maintainer)` in a text stays a line of that text, and so does a fence of the text's own, whatever its length. The prompt tells the AI that a fence holds only that person's text, whatever it looks like.
- **What GitHub doesn't show, the AI doesn't read.** Shown is what the page shows, also after a click on it, as the content of a `<details>` or the popup of a point of a map, with one exception, a comment that GitHub shows collapsed (see below); not what it only copies to the clipboard, shows only on hover or only to a screen reader, or only to someone who edits the issue. The tag characters of Unicode, U+E0001 to U+E007F, spell a whole sentence in ASCII that no browser shows, and zero-width spaces, joiners and the controls of the direction of writing hide or reorder text. The assistant removes every format character of Unicode and every code point that Unicode calls default ignorable, such as variation selectors, which can carry a byte each, from the issue and its comments, from the excerpts of the other issues and discussions, and from the AI's answer before its checks, so that none can hide a token from them either. They go after the HTML, which goes as GitHub hides it: a zero-width space in the `-->` of an HTML comment keeps the comment from ending on GitHub, so that it hides the rest of the text, and taken out first, it would end the comment and show the AI what GitHub hides. A `<!--` without its `-->` hides the rest of the text wherever GitHub hands it on as HTML: at the start of a row, also of a quote, a list item or a footnote, after a tab and at any depth of them, and anywhere in a row of an HTML block, such as one that starts with `<div>`, `<p>` or `<?php`, also after the end of the quote or the list item that holds the block, and after a `--!>`, which ends a comment for GitHub's HTML parser but not the block. So does a quoted value of a tag in such a block that the block doesn't end, since GitHub looks for its end in the rest of the text. A comment of such a block ends only at a `-->` that the block holds: one below the end of the quote or the list item in which the comment starts, such as `1. <!--` above an unindented `-->`, or below a blank row that ends a block of `<div>`, is text for GitHub, and the comment hides the rest of the text. In a paragraph, GitHub shows such a `<!--` as text, and the AI reads it with what follows. Where it is hard to tell whether a row belongs to a block, such as in fenced code or after the end of a quote, the assistant takes the rest out rather than leave it. The excerpts of the other issues and discussions lose their HTML the same way, every tag with its attributes, before the answers of a form become lines. And the invisible characters go before the fence is chosen, so that none can split a run of backticks that would end it.
- **Nor does it read a character reference of one.** GitHub reads a character reference as the character itself, so `&#xE0041;`, `&#917569;` or `&ZeroWidthSpace;` shows as nothing on the page, as U+E0041 and a zero-width space do, and a row of references of the tag characters spells a sentence that no reader of the page sees. The assistant takes each reference of a character that it removes out with the characters, from the issue, its comments, the excerpts of the other issues and discussions and the addresses of the attachments, and the notice counts it with them: in hex or in decimal, with leading zeros, with or without its `;`, a name with its `;`, such as `&shy;`, `&zwj;` or `&it;`, and `&shy` without it, also before a letter, since GitHub reads all of these in the text of an HTML block. In Markdown, GitHub shows some of them as text: a number without its `;` or with more than eight digits, and a reference after a backslash. The assistant takes those out as well, the safe side, whose price is that the AI misses such a reference where the page shows it. A name without its `;` stays, such as `&it` in `for (auto &it : items)`, since GitHub shows it as text everywhere but `&shy`, as do a number too large for a character, `&#0;`, a surrogate, `&amp;#xE0041;`, whose `&` belongs to `&amp;`, and the reference of any other character, such as `&lt;`. Code keeps its references, as GitHub shows them as they are written, such as `auto p = &it;` in fenced code: code counts where it surely is, in the text as it is written. That is fenced code from a fence at the very start of a row to the fence that closes it, without the word after the fence, which GitHub reads as the language, and a code span on one row before which no backtick of its paragraph is left open, and no `<`, backslash or pipe can make it text. Fenced code in a quote or a list item, indented code and code from the row on which HTML could start a block, where GitHub reads the references of the text of the block, lose theirs: the safe side again. The titles of the issues and discussions and the names of categories lose every reference of such a character, also in a code span, since nobody has checked what GitHub shows there. The AI's answers and the attached files keep theirs: GitHub never reads them as Markdown, so it shows a reference there as text. An address that holds such a character or a reference of one, in the target of a link, alone or between `<` and `>`, is no attachment: GitHub links it with the character in it, a dead link, since it serves a file only under the name it was uploaded with. The assistant looks for them before anything goes, so that taking the character out can't lead the AI to a file that the page doesn't link.
- **Nor does it read a tag that runs over several rows.** GitHub reads each row of an HTML block up to the `>` of a tag as part of the tag, past a `>` in a quoted value, also in a quote or a list item, whose marks are no end of it, and up to the end of the block when no `>` comes, or on into an HTML block that follows it; and in a paragraph, a tag that CommonMark reads as one over its rows, such as `<span` above `title="a">`. The assistant takes out such a tag with every row of it. What GitHub shows as text stays: `<a` above a row that starts a quote, a tag of a paragraph that CommonMark doesn't read as one, the tags that GitHub's filter shows as text, such as `<script`, and a tag in fenced code, also in a quote or a list item, which GitHub shows as it is. A tag on one row goes as it always did, but whole where a quoted value holds a `>`: GitHub's HTML parser reads on to the `>` after the value, in an HTML block, a quote or a list item, and in a paragraph, a heading or a cell of a table wherever CommonMark reads the tag as one, so `x <span data-x=">words">y</span>` shows `x y`, and so does a `title` with such a `>`, which the page shows only while the pointer rests on the tag. A tag that CommonMark doesn't read as one stays text, as GitHub shows it, such as `x <span 1=">words">`, of which the assistant takes out the part up to the first `>`, as before. The same goes for a tag right after an instruction whose first `>` comes at once, `<?>`, which GitHub's HTML parser ends there and reads what follows as HTML; for a tag that starts a lazy row below a block of a quote or a list item, which starts a paragraph; for a tag after markup that ends on its row of a list item, which goes on in the rows of the item, since a tight list hands them on without a paragraph; and for a name `=` at the start of a row, whose quoted value runs on. Where it is hard to tell whether a block or fenced code holds a row, the assistant takes the tag out with it, and where it is hard to tell whether a tag goes on in the next block of a quote or a list item, the rest of the text: a block of a quote takes no row without the `>` of the quote, nor a block of a list item a row with less indentation, but a row can't always tell which quote or list item it belongs to.
- **Nor does it read the content of a video or of the brackets of ruby.** GitHub keeps a `<video>` with all that it holds, which is for browsers without video and which no browser shows, and an `<rp>`, the brackets of ruby, which browsers hide: text, but also paragraphs, headings, lists, links and images. The assistant takes out such content up to where GitHub's HTML parser ends the element: at its end tag in the same paragraph, heading or HTML block, or alone on a row after a blank row at the top of the text, and not indented once a list item may hold it, as GitHub's parser ignores it there, one for each start tag of its name, also `<video/>`; for an `<rp>` in a `<ruby>` of the same row also at the `</ruby>` and the next `<rt>`, `<rp>`, `<rb>` or `<rtc>`; otherwise at the end of the paragraph or the heading, or of the text. An end tag in a later paragraph ends nothing, as for GitHub. No link or image inside counts as an attachment. What GitHub shows stays: the text of the `<ruby>` and of an `<rt>` outside an `<rp>`, what follows the end tag, a tag in code, and the content of a `<details>`, which GitHub shows on a click. Where it is hard to tell, the assistant takes out more: after a backtick of the content, which may start code that holds the end tag, after a fence, after the start of an element such as `<p>` or `<div>` in a block, which GitHub's parser keeps open, and in a quote, a list item or a cell of a table, whose end the content may reach.
- **Nor does it read what a `<relative-time>` holds.** GitHub keeps `<relative-time>`, the element in which it shows its own dates, with its `datetime` and all that it holds, and its script for the element draws a date from the `datetime` in its place, such as "on Jan 1, 2020", and nothing of what the element holds: text, but also paragraphs, headings, lists, links and images. The assistant takes out such content as that of a `<video>`, with the same ends, also `<relative-time/>`, and a second `<relative-time>` inside goes with the first. In the place of the element the AI reads a space: the page draws a date there, so `Value<relative-time …>x</relative-time>Error` stays two words for the search, and the AI reads no date. A `<video>` and an `<rp>` leave nothing in their place, as before: neither draws words there. No link or image inside counts as an attachment, and a ticked box beside the element stays ticked. It goes whatever the `datetime` says, since the assistant can't tell which dates the browser reads, and in any case of its name, since GitHub could start to keep `<Relative-Time>`: the safe side. Its price is that the AI misses words that the page shows. The page shows the words of an element without a `datetime`, with one that the browser can't read or with a start tag in another case than lower case, which the sanitizer drops, and an element without a date shows the words of a dated one inside it too. Until the assistant reads where GitHub ends an open element in a quote, a list item or a cell, as for a `<video>`, the AI also misses what follows such an open element there. Code shows the element as it is written: in fenced code, and in a code span that the assistant is sure of, nothing of what it holds goes. Elements of other names with a hyphen, such as `<copilot-directive>` or `<tracking-block>`, keep their text, as the page draws it.
- **Nor does it read what a void element holds inside `<svg>` or `<math>`.** GitHub's sanitizer drops the tags of `<svg>` and `<math>` and keeps their text, but its HTML parser makes no element void inside them, and none breaks out of them: a `<br>`, `<hr>`, `<img>` or `<source>` there holds all that follows it, text, links and images, and GitHub writes none of it, as a void element holds nothing. So `a <svg><br> inner</svg> b` shows `a`, a line break and `b`. The assistant takes out what a start tag of any void element holds there, in any case of its name and not after one that closes itself with `/>`, so that a change of the sanitizer can't open a gap: up to the end tag that closes the outermost `<svg>` or `<math>`, which GitHub reads as `</svg>`, not as `</svg >`, or to the end of the paragraph or the heading that holds the tag, and in an HTML block or a list item, whose end GitHub's parser may find later, to the end of the text. An `<svg>` or a `<math>` opens in a paragraph up to its end, and in an HTML block, such as `<svg>` alone on its row, past blank rows up to its end tag or the end of the text, as on GitHub. The void tag stays, and the image of an `<img>` counts as an attachment; in place of what it holds the AI reads a space, as the page shows a line break, a rule or an image there. Code shows the tags as they are written: in fenced code, and in a code span that the assistant is sure of, nothing opens. Its price is that the AI misses words that the page shows: after one of the 13 other void elements, whose tags the sanitizer drops with nothing hidden; after an end tag that GitHub reads as the end of what the void element holds but the assistant can't tell apart safely, such as `</g>`, `</b>`, `</p>`, an inner `</svg>`, an end tag after a backtick, a `$`, a `[` or a fence of tildes, and an enclosing `</div>` or `</details>`; after a `<br>` in an element where GitHub reads HTML again, such as `<foreignObject>` or `<mi>`; and to the end of the text after a void element in a list item or an HTML block. A search of the issues and pull requests of the repositories of its maintainer found four with a literal `<svg` or `<math`, three in code spans, none that would lose a word. Inside `<svg>` and `<math>`, the void elements also count for the depth below, as every other element does.
- **Nor does it read what such a void element holds past the end of a paragraph whose `<p>` closed before the `<svg>`.** GitHub ends a paragraph with its own `</p>`, which closes an `<svg>` or `<math>` in it, and with it what a void element holds there. But a tag before the `<svg>` may close the `<p>` of the paragraph first: a start tag such as `<div>`, `<hr>`, `<li>` or `<table>`, the end tag `</p>`, or the end tag of an element around the paragraph, such as the `</h1>` of a heading, the `</blockquote>` of a quote, a `</table>` in a cell or the `</div>` of an HTML block above. Then GitHub's `</p>` closes nothing, the `<svg>` stays open past the end of the paragraph, and a `<br>` in it hides everything after it: `x <div><svg><br>`, a blank row and `more words` show only `x`. The assistant notes where the `<p>` of each paragraph closes as it reads the tags, once and from the front: a start tag counts before the outermost `<svg>` or `<math>`, and an end tag anywhere before the void tag, of any name but those that GitHub keeps the `<p>` open around, such as `<span>`, `<b>`, `<a>`, `<code>`, `<img>`, `<label>` or `<font>`; an end tag counts whether or not an element of its name is open, which the assistant can't tell safely. Only a tag that CommonMark hands on counts, not one after a `\` or in a code span, but the `<div>` of `x <https://e.com/<div>>` does, since an autolink holds no `<`. Where the `<p>` is closed, what the void tag holds runs to an end tag that closes the outermost element, also one alone on a later row, or to the end of the text. In a later paragraph, whose `<p>` GitHub opens inside the element, a void tag holds to the end of that paragraph, or to the end of the text after a `</p>` before it; a start tag there closes nothing, as inside the element anywhere. The same holds in the content of a `<video>` or an `rp`, which a tag that closes the `<p>` closes as well. In a heading, only an end tag of its row counts, as GitHub ends the element with the heading after a start tag; and a `#` indented by four columns or a tab starts no heading, since its row goes on the paragraph above, as on GitHub. Its price is that the AI misses words that the page shows: after an end tag that closes nothing, such as a stray `</div>` or `</td>`, or that closes the element with the `<p>`, such as the `</p>` of `x <svg></p><br>`, since an `<svg>` after it would stay open; after `<p>` and after a start tag of a name that GitHub keeps the `<p>` open around but the assistant doesn't list, such as `<foo>`; after a tag in a comment, an attribute or the target of a link; in a cell of a table and below a heading underlined with `===` or `---`; and after the end of a quote, an HTML block or a `<details>` around the element.
- **Nor does it read an instruction, a declaration or a section of CDATA.** GitHub's HTML parser reads `<?`, `<!` with anything but `--` after it, and `</` without a name as a comment up to their first `>`, and shows nothing of it: `<?php echo 1; ?>`, `<!DOCTYPE html>` and `<![CDATA[ … ]]>`. In a paragraph, CommonMark hands one on as HTML where its end follows in the paragraph, `?>` for an instruction, `]]>` for a section of CDATA and `>` for a declaration, also over several rows of a quote, whose marks are no end of it; in an HTML block, and as a block of its own, which only its end ends, GitHub hides each up to its first `>`, up to the end of the quote or the list item that holds the block, or up to the end of the text. The assistant takes each out as far as GitHub hides it, and what follows its first `>` reaches the AI, as GitHub shows it. What GitHub shows as text stays: `</ x>` and `<!X` without its `>` in a paragraph, and fenced code, also in a quote or a list item. Where it is hard to tell, the assistant takes out what GitHub may show: a declaration with a small letter, such as `<!doctype html>`, which GitHub's renderer shows as text but CommonMark has read as HTML since its version 0.30, and an instruction in code of a row or in indented code, which the assistant doesn't follow.
- **Nor does it read a definition that GitHub hides.** GitHub shows nothing of a link reference definition, such as `[//]: # (a comment)` or `[x]: <> "a comment"`, the usual ways to write a comment in Markdown, and nothing of a footnote that no reference shows. The assistant takes both out of the issue, its comments and the excerpts of the other issues and discussions, after the HTML and outside code, and leaves `(link definition removed)` or `(footnote removed)` in the place of each, so that the AI doesn't wonder about the missing target of a `[text][label]` link. It reads them as GitHub does: a definition starts a block, also in a quote or a list item, after indented code and after HTML in a quote or a list item, and its label or title can run over several rows, while a row that looks like one in the middle of a paragraph or in fenced code stays, as GitHub shows it. A row of `=` or `-` ends a definition only where it can underline a heading: `[x]:` above `=` stays a heading, but a definition runs on over such a row without the `>` of its quote or the indentation of its list item, as GitHub reads it. Where Markdown is hard to follow exactly, such as an indented row, which may be code or belong to a list item, or a text whose HTML could start a block, the assistant takes out a definition rather than leave it. Where GitHub hides the rest of the text, such as after a `<!--` in an HTML block or an open `<video>`, it hides every footnote with it, since it shows the footnotes after the end of the text, and the assistant takes each out. A footnote stays only for a reference that GitHub surely shows: not one in code, also in a quote or a list item, in an indented row, after a backslash, in the target of a link, in a definition or a footnote, or in a text whose HTML could hold it, since one of those could be hidden itself. A CommonMark parser checks that no definition is left, and that each footnote left has a reference. A notice in the log counts them.
- **Nor does it read a cell that a table drops.** GitHub shows as many cells of each row of a table as its header has, and drops the rest without a trace. It splits a row at every pipe that comes right after no backslash, however many backslashes come before it, before it reads anything else of the row: also in code, in the text of a link, in a value of a tag and in a comment. The assistant finds a table where GitHub does, a delimiter row of as many cells below the last row of a paragraph, also in a quote, a list item or a footnote, also a header on the first row of a footnote, after its label `[^1]:`, and puts `(cells beyond the header of the table removed)` in place of those cells, in the issue, its comments and the excerpts. A table ends where GitHub ends it, such as at a blank row, another block, a row indented as code or one of other quotes, and those rows stay, as does a table in code or in an HTML block. A row is indented as code four columns in, or four past its delimiter row where a list item or a footnote may hold the table, and the columns count as CommonMark counts them after the marks of a quote: a tab runs up to the next multiple of four from where it stands, and the one column after `>` belongs to the mark, so a tab right after `>` is two columns in, no code. The cells and the HTML are both read from the text as written, and what either takes out goes: taken out first, a cell could take a `<!--` with it, and the HTML the pipe by which GitHub drops a cell. Where it is hard to tell, the cells go. No link or image in such a cell counts as an attachment.
- **Nor does it read the words of a fence.** GitHub shows nothing of the row that opens fenced code but the code below it: the first word of its info string, the text after the backticks or tildes, names the language, which the page shows nowhere, and the words after it, such as `python Some words` or `{.python title="x"}`, are kept only in attributes of the HTML, which no reader sees. The assistant keeps the first word only where it is a plain name of a language: one of the names and aliases of the languages of [GitHub Linguist](https://github.com/github-linguist/linguist), in small letters, which `issue_assistant/code_languages.py` holds, up to a space, a tab or the end of the row, or up to a comma after a name, where GitHub ends one, and without an entity or a backslash. So ```` ```python ```` stays as it is, of `python,x` and `rust x` the AI reads `python` and `rust`, and of `Some-words` or `py&#116;hon` nothing. The rest goes with `(words of the fence that GitHub doesn't show removed)` in its place, from the issue, its comments and the excerpts; no address there counts as an attachment, and none of those words chooses anything for the assistant. The fence, its indentation and the code stay, and so does a drawing, which the first word decides as GitHub reads it, with its entities. The assistant reads the row where GitHub reads one: also in a quote, a list item or a footnote, at the end of a paragraph, of a table or of a quote, unclosed, and as the last row of the text. What GitHub shows stays: a row of indented code, a row inside other fenced code, such as a closing fence with words after it, a row that an HTML block surely holds, as in a `<details>` without a blank row, and a cell of a table. Where it is hard to tell whether a row opens fenced code, as after a tab, below the first list item, or after a fence whose end the cleaning can't tell, the words go: the safe side, whose price is that the AI misses such words where the page shows them as text. The list has about a thousand words, of which each fence can carry only one, and a new release of Linguist needs a new list, as the module says how.
- **Nor does it read the source of a drawing.** GitHub draws fenced code of the languages `mermaid`, `geojson`, `topojson` and `stl` as a diagram, a map or a 3D model, and so a `<pre>` whose `lang` is one of them, up to its `</pre>` as HTML reads it or to the end of the text; the page keeps the source out of view, and no click shows it. The language is the first word of the info string, with its entities read: `Mermaid`, `mermaid,x` and a word with an invisible character stay code, as does such a fence in longer code. Of a diagram, the AI reads what its drawing shows: the source without its comments from `%%`, its `accTitle` and `accDescr`, which only a screen reader gets, and its `click` rows, whose tooltip shows only on hover, each with `(a part of the diagram that GitHub doesn't draw removed)` in its place. A diagram with a directive, front matter, a style or a class, which can draw the rest otherwise, and every map and model lose their whole source to a note; so the AI misses the properties of a map that a click on a point shows. Where it is hard to tell how far a drawn fence reaches, it reaches to a fence that could close it. No address in a drawing counts as an attachment.
- **Nor does it read math that can hide text.** GitHub keeps the TeX of math as it is, and the math renderer of the page draws some of it as nothing: text in a transparent colour or in the colour of the background, a comment from `%`, a `\label` and a `\tag`. GitHub reads `\%` as `%` and the entities in math, such as `&#92;` for a backslash, so no list of commands could tell them all. The assistant keeps math whose source holds no backslash, no `%` and no `&`, such as `$x^2$`, and leaves `(math removed)` in the place of all other math. It finds math as GitHub does: `$…$` and `$$…$$` on one row, `` $`…`$ ``, also with `\$` or an entity in place of `$`, `$$` on rows of their own, and fenced code whose language is `math`, with its entities read, also in list items, quotes, headings and cells, and where a comment over rows joins two rows of math. A dollar sign that GitHub shows as text stays, such as in `it costs $5 and $6`, `$HOME`, in code and in a link, and so does a fence of `Math`, `mathx` or `math,x`, which GitHub shows as code.
- **Nor does it read the title of a link or an image.** GitHub puts the `"…"`, `'…'` or `(…)` after the destination of an inline link or image into its `title`, which the page shows only on hover. The assistant takes it out with the blanks before it, with nothing in its place, as for an attribute of a tag: `[log](https://example.com/a "x")` reads `[log](https://example.com/a)`. The text of the link, its destination and the description of an image stay; a picture that loads shows its description nowhere, which is the price of reading it. No address in a title counts as an attachment.
- **Nor does it take a file from an address that the page doesn't link.** An attachment counts only where its address stands whole in the text as written and the page links exactly that address, as the `href` of a link or the `src` of an image, or shows it as text in code or an HTML block. GitHub's autolink ends a bare address at the first blank or `<` and leaves out trailing punctuation, an unbalanced `)` and a trailing entity such as `&amp;`; the assistant ends it there too, so `…/log.txt.` and `*…/log.txt*` count as `…/log.txt`. Where the page links an address cut or with a suffix, the file counts as what the page links or as none: `…/log<!-- -->.txt` is `…/log`, a file of no kind, `…/files/12<!-- -->345/log.txt`, `…/log.txt'x` and an image upload with letters after it are none, and so is a destination with a comment, a tag, an entity or an escape, which GitHub links percent-encoded or reads, or the `src` of a tag of which only the start is the address. No address counts in the description of an image, which the page shows only where the picture fails, nor in the text of a link, which leads where the link leads, nor in brackets, in which GitHub links nothing; a link, an image or a tag in the text of a link still counts. An address outside ASCII or with a control character, a blank or a backslash, which GitHub links percent-encoded, is none, and none can make the download fail otherwise than as a file that GitHub doesn't serve. Where it is hard to tell, the address counts as none: after a tag, a dollar sign or a backtick that opens no code span closing on its row, in brackets whose `]` may then close nothing, and before a `|`, which ends it in a row of a table only. A code span that closes, as in ``[`log.txt`](…)``, and a `<` that starts no tag, as in `[log <1>.txt](…)`, leave the link as it is. That is the price: the AI misses such a file where the page links it, as `|…/log.txt|x|` in a table without blanks, `[$HOME/log](…)` or `[<b>log</b>](…)`. A search over each character before and after an address, in the text, a destination, an autolink, a `src` and a row of a table, over brackets, code, tags and references, with GitHub's renderer, is kept in `tests/fixtures/attachment-addresses.json` with what the reading loses.

<details markdown="1">
<summary>How the assistant finds a title</summary>

As GitHub does, in the text as written, beside the HTML: after a blank, a tab or one line break, with blanks and a line break before the `)`, in a paragraph, a heading, a cell, a quote, a list item, a footnote and the description of an image. GitHub reads the destination and the title right after the `](`, so a code span, a tag or a comment that starts inside the title changes nothing. A title runs over the rows of its paragraph, also lazy and indented ones, up to a blank row or a row that ends the paragraph, such as a quote, a list item, a heading, a rule, a fence or a block of HTML. What GitHub shows as text stays: code, also a code span that starts before the `](`, an HTML block, an escaped bracket, a destination with a space or with text before its `)`, and a title over a blank row; a quote right after the destination belongs to it. Where it is hard to tell, the title goes, also that of a link around a link, which GitHub shows as text.

</details>

- **Nor does it read text nested deeper than GitHub builds.** GitHub's renderer drops the text inside more than 255 elements, such as a quote of 255 `>` or 128 levels of a list, with everything after it and every footnote; so the assistant counts an upper bound of the depth of each row, with what may stay open around it, and takes out the rest of the text from the first row whose count reaches 128, half of GitHub's limit, and every footnote with it, with a note in its place, for the AI, the excerpts, the attachments and every choice that the assistant makes by itself. Its price is that the AI misses text that GitHub still shows between those depths, such as a list numbered from `1.` to `70.` of bold items; each row of a table and each row of fenced code, also one indented past its fence, counts by itself, as GitHub reads them. The AI's own answers get the same cut, so that none can hide the questions, the links and the footer below it in a comment of the assistant.

- **Nor does it read a comment that GitHub shows collapsed.** Someone with the right to hide comments, from the role Triage on a discussion and Moderate, Write, Maintain or Admin on an issue, or a moderator of the organization, can collapse a comment as spam, abuse, off-topic, outdated, duplicate, resolved or low quality, and the page shows one line and the text only after a click. That is the one text behind a click that the AI doesn't read: the author chose a `<details>`, but someone else chose that the comment doesn't belong to the conversation. The REST API sends `minimized` with every comment of an issue, and GraphQL `isMinimized` with every comment and reply of a discussion; a comment counts as collapsed whenever GitHub says so, also without a reason. `issue.md` and `discussion.md` keep its heading, with its author and date, so that the numbers of the comments stay those of the page, and put a note such as `(GitHub shows this comment collapsed, marked as spam; its text isn't shown.)` in place of its text; the note names one of GitHub's seven reasons or says `hidden`. No file of such a comment reaches `attachments.md`, a reply task judges none, as if it were deleted, a marked answer of another discussion that is collapsed gives no `answer` in `discussions.jsonl`, and a comment of the reporter chooses no language. The assistant follows up on no questions of its own comment that is collapsed and links none in a reminder, a run again doesn't answer a collapsed comment of the reporter a second time, and a collapsed comment of someone who isn't a maintainer teaches no objection to a duplicate. A notice in the log counts the collapsed comments. That is the price: a log or a comment of a maintainer collapsed as outdated or resolved no longer reaches the AI, though the page still shows it after a click.

  What closes, locks or reopens an issue, and what keeps the AI out, counts such a comment as before. A moderator of an organization can collapse comments, but neither close, label nor lock an issue; if a collapsed comment stopped counting there, hiding the reporter's answer would close the issue as unanswered, hiding an objection would close it as a duplicate, and hiding the reporter's comment after a closing would lock it. So the reporter's collapsed answer still answers, a collapsed objection still objects to the sweep, a maintainer's collapsed `/assistant mute` or comment still keeps the AI out, and every comment of the assistant counts for the one-comment rule, the daily limits and the reminders, also when it is collapsed. The event job never sees a collapsed comment: GitHub sends the event when a comment is written, before anyone can collapse it, and none when it is collapsed.
- **Nor does it choose anything for the assistant.** What the assistant decides from a reporter's words without the AI, it decides from the text as the AI reads it, cleaned as above: the words of the search for older issues of the repository and of its related repositories, the language of its comments while no analysis has named one, the area that the answer of the form chooses, with its label and its owners, and whether the description of a merged pull request denies that it fixes an issue. So a name of an error in an HTML comment, an attribute, a link reference definition or the words of a fence starts no search, a paragraph in another language in a comment, such as the instruction of a Markdown template, chooses no language, and a second answer of the area in a comment chooses no label. These choices read a space where the AI reads a note, so no word of a note counts for the language, and `Value` and `Error` on both sides of a drawing stay two words. The definitions are found in the text with the notes, so a row that held only math keeps the words below it. A drawing or math between `doesn't` and `close #12` leaves one clause: the issue stays open. What the cleaning keeps, the description of a Markdown image and the target of a Markdown link, still counts, as it does for the AI; a title no longer does. A character reference reads as its character, as GitHub reads it in Markdown, outside code: `doesn&#39;t close #12` denies, `- [&#120;]` and `- &#91;x]` tick the box, `Auto&shy;mated` is the heading of the box and `Type&ZeroWidthSpace;Error` searches for `TypeError`. A reference of a line break reads as a space, so that no row forms that the page doesn't show, and one that could make a block of its row, such as `&#35;## Area` or `-&#32;[x]`, stays as it is written: the page shows `### Area` and `- [x]` as text, with no field and no box. The box of the opt-out is the one choice that reads both texts: it counts as ticked when an answer of its field is ticked in the text as GitHub stores it or as it shows it, so that a reporter's open fence can't hide it and a box that the page doesn't show can't untick it. Hidden text can only keep the AI out, never let it in.

Every analysis reads the excerpts of every open issue and of the closed ones that changed last, so a text planted in one issue reaches the AI again with each new issue. Its worst use would be to call new issues its duplicates, which close on their own. So only an original that a maintainer vouches for can close another issue:
